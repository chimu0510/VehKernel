# Host and companion setup uses a role-based Python 3.10+ stdlib CLI with udev and user systemd templates

Firmware builds, SITL, and host tests are pinned inside the development container (ADR-0016), but everything outside the container still ran on unverified host state: Docker itself, OpenOCD, `stm32flash`, `pyserial`, `dialout` and `plugdev` group membership, USB udev rules, `ModemManager` and `brltty` mitigation, ROS2 Jazzy with `build-essential` and `colcon` on the companion computer, and RViz2 on a desktop machine. Scattering those steps across prose left fresh machines failing on missing packages (`build-essential` when building the Bridge), permission errors on ST-Link or serial devices, board resets when `ModemManager` probed C50C V1.1's `SERIAL2` download circuit, and `/dev/serial/by-id/` collisions between the C50C V1.1's two CH9102F adapters.

The decision: **host and companion setup is automated and verified by a single role-based CLI (`tools/setup/vk_setup.py`) written in the Python 3.10+ standard library, paired with committed udev rules, user `systemd` templates, `ntp_offset.py`, and a worktree-safe `vk` container wrapper (spec 0017).**

- **Composable roles**: `vk_setup.py` separates machine responsibilities into four composable `--role` profiles: `dev` (Docker, pre-built `ghcr.io/chimu0510/vehkernel-dev` image pull or local build, and `~/.local/bin/vk`), `flash` (`openocd`, `stm32flash`, `python3-serial`, `dialout`/`plugdev` groups, udev rules, and `ModemManager`/`brltty` mitigation), `companion` (ROS2 Jazzy apt repository, `build-essential`, `colcon`, `rosdep`, serial permissions, optional Bridge build, and optional user `systemd` service), and `desktop` (RViz2, `ros-jazzy-rviz-imu-plugin`, `ros-jazzy-teleop-twist-keyboard`, and `ROS_DOMAIN_ID`/firewall checks). Every role supports `--dry-run` to preview changes and `--check` as a read-only doctor that exits non-zero with corrective actions on failure.
- **OS support boundaries**: Ubuntu 24.04 (`noble`, `amd64` and `arm64`, including Raspberry Pi 5) is supported for all four roles. Debian 12 (`bookworm`, including Raspberry Pi OS) is supported for `--role flash` and the bundled host tools. Requesting `dev`, `companion`, or `desktop` on an unsupported distribution (such as ROS2 Jazzy on Debian 12, ADR-0027) fails fast with a clear message. Non-Debian Linux distributions, macOS, and native Windows hosts are out of scope; Windows users run Ubuntu 24.04 under WSL2.
- **Pure Python 3.10+ standard library and thin POSIX `sh` wrapper**: `vk_setup.py` and `ntp_offset.py` have zero third-party runtime dependencies and obey the same Python 3.10 compatibility floor as the other bundled host tools (ADR-0026), checked by `ruff` (`tools/setup/ruff.toml`), `pytest`, and CI's Python 3.10 job. `tools/setup/vk` is a thin POSIX `sh` wrapper (syntax-checked with `sh -n`) so container invocations have minimal start-up overhead while handling TTY detection, git worktree `.git` common-dir read-only mounts, host UID mapping with `HOME=/tmp`, `safe.directory`, and `VK_IMAGE` fallback to a local `vehkernel-dev:latest` image.
- **Udev rules (`tools/setup/udev/99-vehkernel.rules`)**: grants non-root access (`MODE="0660"`, `TAG+="uaccess"`) and sets `ENV{ID_MM_DEVICE_IGNORE}="1"` for STMicroelectronics ST-Link probes (`0483`, group `plugdev`) and WCH CH9102F serial adapters (`1a86:55d4`, group `dialout`). No static `SYMLINK+=` is attached to CH9102F by VID:PID alone because boards such as the C50C V1.1 expose two identical CH9102F adapters; instead, the file carries a commented `ENV{ID_PATH}` and `KERNELS` template for pinning `SERIAL1` (`/dev/vehkernel-link`) and `SERIAL2` (`/dev/vehkernel-download`) by physical USB port.
- **User `systemd` service for the Bridge (`tools/setup/systemd/vehkernel-bridge.service`)**: installed optionally under `~/.config/systemd/user/vehkernel-bridge.service`, configured by `~/.config/vehkernel/bridge.env` (`bridge.env.example`), and enabled at boot with `loginctl enable-linger`. Because it is a user unit rather than a system unit, `tools/flash/deploy.py` can stop an active Bridge before serial flashing and restart it afterwards over non-interactive SSH without `sudo` prompts or `/etc/sudoers.d` rules (ADR-0027).
- **Pre-built multi-arch devcontainer images**: CI publishes `linux/amd64` and `linux/arm64` images to `ghcr.io/chimu0510/vehkernel-dev` from `.devcontainer/Dockerfile` (ADR-0016), so `--role dev` does not force every contributor to rebuild from `snapshot.ubuntu.com`, while retaining local `docker build` as a first-class fallback.
- **Shipped in the host tools bundle**: `tools/setup/` travels inside the host tools bundle (ADR-0026) so a companion computer can check or repair its setup and measure clock offset (`ntp_offset.py`) without a git checkout.

## Considered Options

- **Ansible playbooks and roles**: rejected. Ansible requires installing its runtime on the target or maintaining a separate control machine and inventory, adds a third-party toolchain outside the host tools bundle, and is heavier than a single developer or companion computer needs for four small roles.
- **Nix or NixOS**: rejected. Nix imposes a steep adoption barrier on robotics users running standard Ubuntu 24.04 or Raspberry Pi OS images, integrates poorly with upstream ROS2 Jazzy apt repositories and host udev/systemd services, and duplicates what the development container already solves for firmware builds (ADR-0016).
- **ROS2 in Docker on the companion computer**: rejected, consistent with ADR-0027. Most companion setups run ROS2 natively alongside other nodes and hardware drivers; containerizing the Bridge complicates serial device access, DDS discovery, and coexistence with user colcon workspaces.
- **A shell script installer (`setup.sh`)**: rejected for the main setup CLI (retained only for the thin POSIX `sh` `vk` wrapper). OS matrix validation, idempotent `--check` diagnostics, `--dry-run`, and fake-injected unit tests are cleaner and more reliable in Python 3.10+ stdlib, and reuse the existing `ruff`, `pytest`, and Python 3.10 CI coverage without adding `shellcheck` to the development container.
- **A system-wide `systemd` service (`/etc/systemd/system/vehkernel-bridge.service`)**: rejected. Letting `tools/flash/deploy.py` stop and restart a system service over non-interactive SSH would require passwordless `sudo` rules in `/etc/sudoers.d`. A user unit with lingering starts at boot and stays under the unprivileged user's control.

## Consequences

- `tools/setup/` shares the Python 3.10 floor of the other bundled host tools (ADR-0026); newer Python syntax is rejected by `tools/setup/ruff.toml` and CI.
- Adding a user to `docker`, `dialout`, or `plugdev` takes effect only in a new login session; `vk_setup.py` reports when re-login is required instead of hiding it in a `newgrp` subshell.
- Supporting a new Linux distribution or a later ROS2 LTS release is a deliberate change to this ADR, ADR-0027, and `vk_setup.py`'s OS table.
